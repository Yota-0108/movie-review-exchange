# 映画感想ランダム交換システム - 開発プロンプト

## プロジェクト概要
ランダムマッチングによる非同期の映画感想共有システム。同時刻に投稿された感想を相手を選ばずランダムに受け取る、という交換ゲームの仕組みからアイデアの着想を得ている。
1-1のリアルタイム交換ではなく、投稿された感想をDBに蓄積し、受け取り手が区分・年代・タグ等の条件を選んでランダムに1件抽出する設計。

Movie DB(PostgreSQL/Supabase, Node.js, Render)の拡張プロジェクトという位置づけ。
今回はAWS完全移行で構築する。

---

## コア要件

### 1. 投稿フォーマット(2領域構成)
感想は1件につき2つの領域を持つ。

- **領域A(ネタバレなし・必須)**
  - 作品タイトル、公開年、区分(邦画/洋画・実写/アニメ)
  - 「特に良かった要素」タグ(音楽/アクション/演技/脚本/演出/映像美/テンポ/衝撃展開など、事前定義された選択式タグ)
  - ネタバレを含まない前提の項目のみ

- **領域B(自由記述・任意開封)**
  - 受け取り手が任意で開封できる自由記述欄
  - ネタバレを含んでよい

この分離により、ネタバレを避けたい人・感想を読んでから鑑賞判断したい人の両方に対応する。

### 2. 受け取り方式
- 1-1の同期交換ではなく、**DBからの条件付きランダム抽出**
- 受け取り手は区分(邦画/洋画、実写/アニメ)・年代・投稿者が選んだ魅力タグ(音楽/アクション等)でフィルタをかけられる
- フィルタが強いほど母数が枯渇しやすいため、**母数が少ないカテゴリでは「未読優先」ロジック**を検討(同じ投稿ばかり引かないようにする)
- 自分が投稿した感想は、自分のランダム受信では返さない(自演いいね対策と同じ発想。セレンディピティを狙う機能で自分の投稿が返ってきても意味がないため)

### 3. 書く動機の設計
- ランキング化はしない(いいねによる序列・人気順ソートは作らない)
- いいね機能自体は残すが、**通知程度の軽い承認シグナル**に留める(集計表示のみ、ソート・フィルタには使わない)
- 主な動機はFilmarksモデルを参考に、「自分の観賞記録を残す」という個人的な動機の副産物としてDBに蓄積される設計を目指す
- 重複いいね対策(同じユーザーが同じ感想に複数回いいねすること)として `(review_id, user_id)` を複合主キーとする(DB構造で保証)
- 自演いいね対策(投稿者本人が自分の感想にいいねすること)は複合主キーだけでは防げないため、Lambda側でレビューの所有者(`reviews.user_id`)といいねしようとしているユーザー(リクエスト元の`user_id`)を比較し、一致する場合は拒否する(アプリケーションロジックで保証)

## DBスキーマ(正規化済み)

```sql
-- ユーザー
users
- user_id (PK)  -- Cognitoのsubをそのまま格納。不変・自動発行・一意
- username       -- 表示名。変更可能・重複あり(user_idしか他テーブルから参照しないため問題ない)
- avatar_key (text, nullable)  -- S3上のプロフィール画像パス。画像本体はDBに入れず、S3に保存してキーのみ持たせる。未設定ならnull(デフォルトアイコン表示)
- created_at

-- 作品マスタ
films
- film_id (PK)
- title
- release_year
- country_type  -- enum: 邦画/洋画(1作品につき1つ)
- format_type   -- enum: 実写/アニメ(1作品につき1つ)
- UNIQUE(title, release_year)  -- 重複登録防止

-- タグマスタ(事前定義、ユーザーの自由入力は不可・表記揺れ防止)
tags
- tag_id (PK)
- tag_name  -- 例: 音楽, アクション, 演技, 脚本, 演出, 映像美, テンポ, 衝撃展開

-- 感想
reviews
- review_id (PK)
- user_id (FK -> users, ON DELETE CASCADE)
- film_id (FK -> films, ON DELETE RESTRICT)
- body (text, nullable)  -- 領域Bの自由記述
- created_at

-- 感想とタグの中間テーブル(多対多)
review_tags
- review_id (FK -> reviews, ON DELETE CASCADE)
- tag_id (FK -> tags, ON DELETE RESTRICT)
- 複合主キー: (review_id, tag_id)

-- いいね(複合主キー版・like_idは持たない)
likes
- review_id (FK, PK -> reviews, ON DELETE CASCADE)
- user_id (FK, PK -> users, ON DELETE CASCADE)
- created_at
```

### 外部キーのON DELETE方針
- `review_tags.review_id → reviews`:**CASCADE**(感想削除時、タグの紐付けも一緒に削除。残す意味がないデータのため)
- `likes.review_id → reviews`:**CASCADE**(感想削除時、いいねも一緒に削除)
- `received_reviews.review_id → reviews`:**CASCADE**(感想削除時、受信履歴も一緒に削除。存在しない感想への参照を残さない)
- `reviews.film_id → films`:**RESTRICT**(作品マスタは運営管理の基盤データのため、感想が紐づく作品を誤って削除できないようにする)
- `review_tags.tag_id → tags`:**RESTRICT**(タグも運営管理の基盤データのため、使用中のタグを誤って削除できないようにする。filmsと同じ考え方)
- **`user_id`系の外部キー(`reviews.user_id`、`likes.user_id`、`received_reviews.user_id` → `users.user_id`)は`CASCADE`で確定**:退会(`DELETE /users/me`)時、そのユーザーに紐づく投稿・いいね・受信履歴を全て削除する
  - 検討したSET NULL案(投稿は匿名化して残す)は、感想の蓄積というサービス側の都合を優先した設計になってしまうため見送った。「退会すれば自分に関するデータは全て消える」という、ユーザーの意思をそのまま反映できるCASCADEを採用する
  - ログアウト(`POST /auth/logout`)とは明確に別の操作。ログアウトはセッション終了のみでデータは一切変更されない不可逆でない操作、退会はアカウントとデータを完全に消去する不可逆な操作

設計の意図:
- タグは正規化(tagsテーブル+中間テーブル)を採用。将来「タグ別の集計・分析」をしたい構想があるため、`text[]`型での非正規化は見送った
- reviewsにタイトル・年代・区分を直接持たせず、filmsへのFKのみを持つ(重複防止)
- likesは`(review_id, user_id)`の複合主キーとすることで、「同じユーザーが同じ感想に複数回いいねできない」制約を主キー自体で保証する(別途ユニーク制約は不要)。Filmarksのような「いいね状態の保持」は、行の存在/非存在で管理する(付ける→INSERT、外す→DELETE。API側は`PUT`/`DELETE`に分離し、冪等性を保つ設計とする)
- filmsの`genre`という1カラムに「邦画/洋画」「実写/アニメ」「ジャンル(アクション/ドラマ等)」という異なる属性軸が混在していたため、`country_type`・`format_type`の2つのenumカラムに分離した。ジャンル(アクション/ドラマ等)は作品マスタ側に持たせず、投稿時にユーザーが選ぶ「良かった要素」タグ(音楽/アクション/ヒューマンドラマ等)がジャンル的な情報も兼ねると判断し、tags側の表現に一本化した
- `email`はusersテーブルに持たせない。Cognitoが認証基盤側でメールアドレスを既に管理しており(確認コード送信・パスワードリセット等はCognito内部で完結)、アプリDB側でメールアドレスを使う機能(通知等)が現状スコープにないため、複製して保持する必要がないと判断した。将来メール通知機能が必要になった場合はCognito Admin API経由で取得する前提とする

## インフラ構成(AWS)

### 前提
- 収益を目的としないポートフォリオ/個人開発。予算制約が大きい
- 「常時起動」が理想だが、コスト面で非現実的と判断し、Aurora Serverless v2を採用

### DB: Aurora Serverless v2
- エンジン: Aurora PostgreSQL(0 ACU対応バージョン: 13.15+, 14.12+, 15.7+, 16.3+のいずれか)
- 最小ACU: 0(ゼロスケール対応)
- 一時停止までの待機時間: **初期値24時間**(短時間の待機時間だと通常利用時の体感速度が落ちるため、立ち上げ期は「誰も使わない日だけ止まる」設計にしておく)
  - 運用開始後、CloudWatchでの利用状況と実際の請求額を確認し、アクセスが少ない期間が明確になれば1時間程度まで短縮するなど、実測に基づいて調整する
  - AWS Budgetsで予算アラートを設定し、UX(コールドスタートの体感)とコストの両方を実測しながらバランスを調整する
- 最大ACU: 低めに設定(想定外の高額請求を防ぐ。ただし、TOHO-ONE障害の考察を踏まえ、"予測可能な負荷急増イベント"がある場合は一時的な引き上げも検討)

### 認証: Amazon Cognito
- ユーザープールで認証管理
- パスキー対応も視野に入れる

### セキュリティ設計方針

**IAM・アクセス制御**
- IAMロールは最小権限の原則。Lambda関数ごとに必要なリソースのみにスコープを絞る
- 個人特定情報(メール等)とプロフィール情報のテーブルアクセス権限を分離

**パスワードのハッシュ化**
- Cognitoが内部で担う。アプリDB(`users`テーブル)にパスワードのカラムは存在せず、アプリ側のコードやDBがパスワードそのものに触れることは一切ない

**SQLインジェクション対策**
- RDS Data APIの**パラメータ化クエリ**を徹底することで担保する。Data API自体はSQL文とパラメータを分離して送る仕組みが標準だが、これは「Data APIを使っているから安全」という意味ではなく、**Lambdaのコードでユーザー入力を文字列結合でSQL文に埋め込むことを禁止する**という実装ルールとして明示する必要がある

**保存時暗号化**
- Aurora、S3、Secrets Manager、CloudWatch Logsそれぞれで保存時暗号化を有効化
- 必要に応じてKMSキーを使用(カスタマー管理キーが必要な範囲を検討)

**転送時暗号化**
- HTTPS/TLSで統一(フロント⇄CloudFront⇄API Gateway⇄Lambda⇄Data API全経路)

**CloudTrail(インフラの変更履歴を追跡)**
「誰が、どのAWSリソースの設定を変更したか」を記録する。以下を監視対象とする。
- IAM変更
- Lambda設定変更
- Aurora設定変更
- S3バケット設定変更

**API Gatewayアクセスログ(アプリの利用状況を追跡)**
CloudTrailとは別の目的・別の仕組み(CloudWatch Logsに出力)。エンドユーザーによるAPI呼び出しの実態を記録する。
- パス
- ステータスコード
- レイテンシ
- request_id

**Lambdaログ**
- バリデーションエラー
- Data APIエラー
- 処理時間

**ログ出力時の禁止事項(機密情報のマスキング)**
以下はいかなるログ(Lambdaログ、API Gatewayアクセスログ含む)にも出力しない。デバッグ目的でリクエストボディ・ヘッダーをそのまま出力すると混入しやすいため注意する。
- パスワード
- JWT(IDトークン/アクセストークン)
- リフレッシュトークン
- 感想本文(`reviews.body`)
- メールアドレス

エラーログには「エラー種別」「発生箇所」を基本とする。`user_id`は、氏名やメールアドレスを直接含まない仮名的な識別子だが、DB内で`username`・投稿履歴・いいね履歴等と紐づけられ、アカウント本人との対応付けが可能なため、無条件に常時出力するのではなく**エラー調査等で必要な場合にのみ**出力する。感想本文が絡むバリデーションエラー等は、本文そのものではなく「文字数」「タグ数」等のメタ情報のみを出力する。

**Auroraログ**
- SQLエラー
- DB内部の問題

## 開発時に踏まえてほしい設計思想
すべての技術選定は「状況が最も不利に転んだ場合」を起点に判断すること。
- コストの最悪ケース(想定外の高額請求)とUXの最悪ケース(コールドスタートによる遅延)は互いにトレードオフの関係にあるため、両方を明示した上でバランスを取る
- 「流行するかどうか」という不確実性に依存しない設計を優先する(バズった場合・誰も使わない場合の両方で破綻しない構成)

## 受信履歴テーブル(未読優先ロジック用)

```sql
-- 誰がどの感想を受信済みか(ランダム抽出時の重複回避)
received_reviews
- user_id (FK -> users, PK, ON DELETE CASCADE)
- review_id (FK -> reviews, PK, ON DELETE CASCADE)
- received_at
```

- `likes`テーブルと同じ複合主キー構造を採用
- 受信可能な感想が0件の場合は無理にフォールバックを行わず、**null(投稿が少ない旨をフロントで表示)** を返す設計とする(誠実さとシンプルさを優先)

### 競合状態(race condition)対策
同じユーザーが短時間に複数回リクエストを送った場合、複数のLambdaが同時に同じ感想を候補として選んでしまう可能性がある(候補選定と受信確定が分離していると発生しやすい)。これを防ぐため、以下のトランザクション処理を採用する。

1. `BeginTransaction`
2. 未受信の候補を1件抽出(SELECT)
3. `received_reviews`へINSERT
4. INSERTが成功したらCommit(この候補が正式に確定)
5. 複合主キー競合(同じ`user_id`・`review_id`の組み合わせが既に存在)でINSERTが失敗した場合はRollbackし、別の候補で再抽選する

DBの複合主キー制約を「審判」として使うことで、アプリケーション側で複雑な排他制御ロジックを書かずに競合を防げる。likesの複合主キー設計と同じ発想の応用。

## API設計(REST)

方針: データ構造がシンプルなためGraphQLは採用せず、REST(API Gateway HTTP API + Lambda)の構成で統一する。

**API Gatewayのタイプ:HTTP API(REST APIではなく)**
- REST APIより料金が安く(一般的に3〜7割程度安価)、機能もシンプルなLambda呼び出しには十分
- 認可には**JWT Authorizer**(HTTP API組み込み機能)を採用。CognitoのユーザープールURLを指定するだけでアクセストークンの署名検証・有効期限・発行者確認を自動で行う。認可用のLambda関数を別途自作する必要がない
- REST API向けの`COGNITO_USER_POOLS`オーソライザーは今回使わない(HTTP API採用のため)
- **注意:JWT Authorizerは何も設定しなければIDトークンとアクセストークンを区別しない**。両方Cognitoが発行した正しい署名のJWTであるため、デフォルトではIDトークンを渡しても認可が通ってしまう可能性がある。AWSはアクセストークンのみを受け入れたい場合、ルートに**認可スコープ**を設定することを推奨している。Cognitoのメール・パスワード認証(今回採用の方式)で発行されるアクセストークンには標準で`aws.cognito.signin.user.admin`スコープが付与されるため、これをルートの認可条件に指定し、実質的にアクセストークンのみを受け入れる設定とする

```
■ 認証系(Cognitoが大部分を担う。API Gateway側はHTTP APIのJWT Authorizerでトークン検証)
POST /auth/signup                -- サインアップ(Cognito呼び出し)
POST /auth/confirm                -- 確認コード検証
POST /auth/resend-confirmation    -- 確認コードの再送(未達・期限切れ時)
POST /auth/login                  -- ログイン、トークン発行
POST /auth/refresh                -- リフレッシュトークンで再発行
POST /auth/logout                 -- ログアウト(リフレッシュトークンの無効化+Cookieのクリア)
POST /auth/forgot-password        -- パスワードリセット用コードをメール送信
POST /auth/reset-password         -- コード+新パスワードでリセットを確定

■ ユーザー
GET    /users/me                    -- 自分の情報取得
PATCH  /users/me                    -- usernameの変更、avatar_keyの更新
POST   /users/me/avatar-upload-url  -- S3への署名付きアップロードURLを発行(画像本体はLambdaを通さず、フロントから直接S3にPUT)
PUT    /users/me/password           -- ログイン中のパスワード変更(Cognitoの`ChangePassword`相当)
DELETE /users/me                    -- 退会。Cognito側のユーザーおよびアプリDB上の関連データ(投稿・いいね・受信履歴)を全てCASCADE削除する不可逆な操作

■ 感想(reviews)
POST   /reviews             -- 感想投稿(領域A+B、タグ含む)
GET    /reviews/me          -- 自分の投稿履歴(観賞ログとして)
PATCH  /reviews/{review_id} -- 自分の投稿を編集。Lambda側で所有者(reviews.user_id)とリクエスト元を照合し、一致しない場合は拒否する
DELETE /reviews/{review_id} -- 自分の投稿を削除。所有者チェックはPATCHと同様。ON DELETE CASCADEにより紐づくreview_tags・likes・received_reviewsも自動削除される
GET    /reviews/received    -- 自分が過去に受信した感想の一覧(received_reviewsとreviewsをJOIN)。オフセットページネーション対応(?limit=&offset=)
POST   /reviews/random      -- ランダム受信。呼び出し時にreceived_reviewsへの記録(副作用)が発生するためPOSTとする
                               リクエストボディでフィルタを指定(全て省略可能)
                               例: { "country_type": "邦画", "format_type": "実写", "tags": ["音楽", "映像美"], "tag_mode": "any" }
                               例(フィルタなし): {}
                               ※ ジャンル(アクション/ドラマ等)は作品マスタに持たせず、tagsに一本化しているため、genresのような別フィールドは設けない
                               ※ tag_modeは複数タグ指定時の絞り込み方式。"any"(いずれか一致、デフォルト) / "all"(すべて一致)。母数枯渇を避けるためデフォルトはany
GET    /reviews/public      -- ログイン不要の公開閲覧(認証Authorizerを外したルート)。received_reviewsへの記録は行わない
                               クエリパラメータ: ?limit=20&offset=0(オフセットページネーション)
GET    /films/{film_id}/reviews  -- 特定作品の感想まとめページ用。ログイン有無を問わず閲覧可能
                               クエリパラメータ: ?limit=20&offset=0(オフセットページネーション)
                               ※ この閲覧経路はreceived_reviewsに記録しない(ランダム受信という受け身の体験と、能動的に探して読む体験を区別するため。未読優先ロジックはランダム受信のみに適用する)

■ いいね
PUT    /reviews/{review_id}/like         -- いいねを付ける(INSERT。既に存在する場合は何もしない=ON CONFLICT DO NOTHING。何度呼んでも結果は同じ=冪等)
DELETE /reviews/{review_id}/like         -- いいねを外す(DELETE。何度呼んでも結果は同じ=冪等)。投稿者本人によるいいねはLambda側で拒否する
GET    /reviews/{review_id}/likes/count  -- いいね数取得

■ 作品・タグ(マスタ参照)
GET  /films/search        -- 作品タイトル検索(投稿時の選択用)。ログイン必須ルート
                             クエリパラメータ: ?q=検索文字列
                             内部クエリ: ILIKE '%query%' による部分一致(大文字小文字を区別しない)、release_year降順でLIMIT 10
GET  /tags                -- 事前定義タグ一覧取得
```

`POST /reviews/random`の内部クエリ方針:
```sql
SELECT * FROM reviews
WHERE review_id NOT IN (
  SELECT review_id FROM received_reviews WHERE user_id = :user_id
)
AND reviews.user_id <> :user_id  -- 自分が投稿した感想は自分のランダム受信で返さない
-- 区分・タグのフィルタ条件(指定時のみ追加)
ORDER BY RANDOM()
LIMIT 1
```
フィルタは全て任意(区分・タグを指定しない完全ランダムも選択可能)。これは投稿数がまだ少ない立ち上げ期に、フィルタが原因で受信できるものがなくなる事態を避けるための設計。

### ログインなし閲覧について
- API Gateway(HTTP API)のJWT Authorizerは**ルート単位で付け外しできる**ため、`GET /reviews/public`・`GET /films/{film_id}/reviews`は認証を要求しないルートとして設定する(DBスキーマ・認証フロー自体の変更は不要)
- ログインしていないユーザーは`user_id`を持たないため、未読優先ロジックや受信履歴の概念は適用できない。これらのエンドポイントは単純な一覧表示(作成日時順等)にとどめる

### ページネーション方式:オフセットページネーション
- `GET /reviews/public`・`GET /films/{film_id}/reviews`ともに`?limit=20&offset=0`形式のオフセットページネーションを採用
- 配列の添字アクセスに近い方式(任意のページに直接アクセスできる)。データ量増加時の速度劣化はカーソルベース方式より起きやすいが、今回の想定規模(films1000本程度、個人開発)では実用上問題にならないと判断
- カーソルベースページネーション(連結リストのように前から順にしか辿れない方式)は、無限スクロールUIとの相性は良いが実装がやや複雑になるため今回は見送り

### 作品まとめページの閲覧とreceived_reviewsの関係
- `GET /films/{film_id}/reviews`経由で読んだ感想は`received_reviews`に記録しない。ランダム受信(受け身の体験)と、作品まとめページからの能動的な閲覧は別の体験として扱い、未読優先ロジックはランダム受信にのみ適用する

## 認証フロー(Cognito)

### 認証方式
- メール+パスワード方式(Cognito標準機能)。パスキー・ソーシャルログインは後回し
- 個人開発では認証基盤を自作しないことを優先し、Cognitoの標準フローに乗る

### トークン運用
- IDトークン/アクセストークン:有効期限1時間(デフォルト)
- リフレッシュトークン:有効期限30日(デフォルト)で開始、運用しながら調整

### トークンの役割分担
- **アクセストークン**:API Gatewayでの認可判定に使用。「このリクエストを実行してよいか」をこのトークンで検証する
- **IDトークン**:`user_id`(sub)を取得するために使用。**`username`の表示にはIDトークンを使わない**(理由は次項)
- **リフレッシュトークン**:アクセストークン/IDトークンが失効した時に、再ログインなしで新しいトークンを再発行してもらうために使用

### usernameはアプリDBから取得する(IDトークンのキャッシュとの食い違いを避ける)
- IDトークンはログイン(または再発行)時点の情報がスナップショットとして固定され、次に更新されるまで内容が変わらない
- アプリDBの`username`は`PATCH /users/me`でいつでも変更可能な設計のため、IDトークンに含まれるユーザー名情報を画面表示に使うと、**変更直後はトークンが再発行されるまで古い名前が表示され続ける**食い違いが起きる
- さらに、Cognitoが管理する「ユーザー名」(サインアップ時の識別用。今回はメールアドレスが該当)と、アプリDBの`username`(表示名、変更可能)は別々に管理されている情報であり、そもそも同期の保証がない
- そのため、**usernameの表示は必ず`GET /users/me`(アプリDB)から取得する**。IDトークンは`user_id`(sub)を取り出す用途にのみ使用する

### トークンの運び方(2種類を明確に区別する)
API Gateway(HTTP API)のJWT Authorizerは、CookieではなくAuthorizationヘッダーに乗せたトークンを見て検証する仕組みのため、トークンの種類によって運び方を分ける。

- **リフレッシュトークン**:httpOnly Cookieに保存(ログイン維持用。API呼び出しには使わない)
  - `HttpOnly`:必須(XSS対策、JSからの読み取り不可)
  - `Secure`:必須(HTTPS通信のみ)
  - `SameSite=Lax`:CSRF対策。外部からのリンク遷移でのログイン状態引き継ぎとCSRF対策のバランスを取った設定
- **アクセストークン**:`Authorization`ヘッダーに乗せてAPI Gatewayの認可判定に使用
- **IDトークン**:フロント側のメモリ(state)に保持し、`user_id`(sub)の取得に使用。username等の画面表示には使わない(常にDBから取得する)
- localStorageへの保存は不採用(XSS時にトークンが即座に読み取られるリスクがあるため。いずれのトークンも対象外)

### 全体フロー
1. ユーザーがメール+パスワードでサインアップ
2. Cognitoが確認コードをメール送信
3. ユーザーがコード入力して本人確認完了
4. ログイン時にCognitoがJWT(IDトークン/アクセストークン)+リフレッシュトークンを発行
5. リフレッシュトークンはhttpOnly Cookieに保存。アクセストークン・IDトークンはフロントのメモリ(state)に保持
6. API呼び出し時はアクセストークンを`Authorization`ヘッダーへ付与してAPI Gateway経由でLambdaにリクエスト。IDトークンは`user_id`(sub)の取得にのみ使用し、username等の画面表示は`GET /users/me`でアプリDBから取得する
7. API Gateway(HTTP API)側でJWT Authorizerがアクセストークンを検証し、正当なら後続のLambdaを実行
8. アクセストークンが失効したら、Cookie内のリフレッシュトークンを使って裏側で自動的に再発行(再ログイン不要)

### user_id / username の設計
- `user_id`(PK):Cognitoの`sub`をそのまま格納。不変・自動発行・一意
- `username`:表示名。変更可能・重複あり(他テーブルからは`user_id`のみを参照するため、重複や変更が整合性に影響しない)

## DBアクセス方式:RDS Data API

### 採用理由
- Lambda⇄Aurora間の接続方式には「直接接続(VPC内TCP接続)」と「RDS Data API(HTTPS経由)」の2択があった
- 直接接続はLambdaの同時実行数増加時にDB接続数が枯渇しやすく、対策としてRDS Proxyを挟む必要があり追加コストが乗る
- **Data APIを採用**。コスト最小化・構成の単純化という方針に合致するため
- Data API採用により、**LambdaをVPCに配置する必要がなくなる**(HTTPS経由でAWS公開エンドポイントを叩く方式のため)。これによりVPC構成が大きく簡略化される(詳細は次項)
- 追加で必要になるもの:Secrets Manager(DB認証情報の管理)へのアクセス権限をLambdaのIAMロールに付与
- トレードオフ:リクエストごとの課金、直接接続よりレイテンシがやや増加する

## VPC・セキュリティグループ構成

### 方針の変更(Data API採用に伴う簡略化)
- Data API採用により、**LambdaはVPCに配置しない**(VPC外の通常のLambdaのまま)
- これに伴い、Lambda用のVPCエンドポイント(Cognito用)は不要になる。VPCに入らないため、NATゲートウェイ回避の検討自体も不要になった
- Aurora自体は引き続きVPC内に配置(マネージドDBとして必要)
- S3用のVPCエンドポイントは、プロフィール画像アップロードの署名付きURL発行等でLambdaがVPC外からS3にアクセスする形になるため、通常のIAM権限で対応可能(VPCエンドポイント自体は不要になる可能性が高い。要検証)

### Auroraへのアクセス制御(攻撃対象領域を狭める設計)
- **Public accessを無効化**:AuroraインスタンスにパブリックIPを持たせない
- **直接TCP接続を許可するインバウンドルールを設けない**:セキュリティグループのレベルで、5432番ポートへの接続を誰にも許可しない(Data API採用により直接TCP接続の経路自体が不要になったため)
- **Data APIの実行権限はIAMで制御**:Data APIはHTTPS経由の呼び出しだが、誰でも呼べるわけではなく、IAMポリシーで許可されたLambdaのロールのみが実行可能
- **DB認証情報はSecrets Managerで管理**:LambdaのコードやIAMロールにはDBのユーザー名・パスワードそのものを持たせず、Data APIが内部的にSecrets Managerを参照する
- 結果として、TCPでの直接アクセス経路を完全に閉じ、Data API+IAM+Secrets Managerという単一の管理された経路のみを開ける構成になる

### AZ要件(訂正)
- Aurora(RDS全般)は仕様上、**DBサブネットグループの作成時点で最低2つのAZに跨るサブネットが必要**(レプリカを持つかどうかとは別の制約)
- 前回「シングルAZで開始」としたのは不正確な表現だった。正確には「**サブネットは2AZに用意するが、稼働するインスタンス(レプリカ)は1つだけに絞る**」という意味になる
- コスト面の判断(2個目のインスタンス代を発生させない)は前回の方針のまま変更なし

### 構成イメージ(Data API採用後)
```
VPC
├─ プライベートサブネット(AZ-a)
│   └─ Aurora Serverless v2(プライマリ)
├─ プライベートサブネット(AZ-b)  ※サブネットグループの要件を満たすために必要。インスタンスは配置しない
│
└─ セキュリティグループ
    └─ Aurora用SG:Data API経由のアクセスのみ許可(直接の外部アクセス経路なし)

Lambda(VPC外)
- Secrets Manager、RDS Data APIへのアクセス権限をIAMロールで付与
- Cognitoへのアクセスも通常のパブリックエンドポイント経由(VPCエンドポイント不要)
```

## フロントエンド構成

### 技術選定
- **React**を採用(Movie DBはVanilla JS/HTML/CSSで実装したが、今回は認証状態・いいね状態・フォーム入力など状態管理が多く絡むため、Reactの宣言的UIが向いている。ES/面接での技術幅を見せる意図もある)
- 状態管理:Redux等は不要な規模。`useState`(コンポーネント単体の状態)と`useContext`(ログイン状態などアプリ全体で共有する状態)の標準機能で足りる

### ホスティング・配信構成(CloudFrontマルチオリジン)
フロント(S3)とAPI(API Gateway)を、CloudFront経由で**同一ドメイン**として配信する構成を採用する(Memory RoadでのCloudFront/S3経験を再利用)。

```
https://example.com/*       → S3(フロントの静的ファイル)
https://example.com/api/*   → API Gateway(HTTP API)
```

- CloudFrontのビヘイビア(Behavior)を2つ設定:デフォルトビヘイビア(`/*`)はS3オリジン、`/api/*`のパスパターンはAPI Gatewayオリジン(HTTP APIのデフォルトエンドポイントを指定)
- ブラウザから見て両方が同一オリジンになるため、**CORSの許可設定が原則不要になる**(以前の未確定事項の1つを構成上解消)
- 同一オリジンのため、httpOnly Cookie(リフレッシュトークン)のクロスオリジン特有の面倒(送信されない、プリフライトリクエスト増加等)も回避できる
- フロントのAPI呼び出しは `https://example.com/api/...` という同一ドメイン配下のパスで統一される

### SSL/TLS設計(独自ドメイン + ACM証明書)
- **独自ドメインを取得する**(CloudFrontのデフォルトドメイン`.cloudfront.net`はURLとして不審に見えやすく、メール+パスワード認証を扱うサービスでは信頼性に直結するため)
- コスト:ドメイン取得費用(`.com`で年間1,000〜1,500円程度)+ Route 53ホストゾーン(月額0.5ドル程度)。ACM証明書自体の発行は無料。AWS Budgetsで実測しながら調整する運用方針の範囲内で吸収できる規模
- **ACM証明書はバージニア北部リージョン(us-east-1)で発行する**:CloudFront用の証明書はこのリージョンでの発行が必須という仕様上の制約があり、東京リージョンで進めてきた今回のプロジェクトでは見落としやすい点
- 証明書の検証方式は**DNS検証**を採用(自動更新と相性が良いため)。検証用のDNSレコードをRoute 53に設定する
- API Gateway(オリジン側)は独自ドメインを使わずデフォルトエンドポイント(`{api-id}.execute-api.{region}.amazonaws.com`)のままでよい。ブラウザから見えるのはCloudFrontの独自ドメインのみのため、オリジン側の証明書管理は不要

### パスの書き換えについて(CloudFront Functions採用)
CloudFrontの`/api/*`ビヘイビアは「一致したリクエストをこのオリジンに送る」という振り分けの機能であり、パスの一部を自動的に削除する機能ではない。Origin Pathも同様に「オリジン側のURLに固定パスを追加する」機能であって、リクエストパスの先頭を削るものではない。つまり何もしない場合、`https://example.com/api/reviews/random`へのリクエストは、`/api/reviews/random`という**そのままのパス**でAPI Gatewayに転送されてしまい、`/api`なしで定義したAPIのルートと一致しなくなる。

対策として**CloudFront Functions**を採用し、ビューアリクエストの段階で先頭の`/api`を削除する処理を挟む。
- CloudFront Functionsを選ぶ理由:Lambda@Edgeより大幅に安価(コスト最小化の方針と合致)。パス書き換えのような軽量な処理には十分
- これにより、API Gateway側のルート定義は`/api`なしの表記(このファイルに記載のAPI一覧のまま)を維持できる

### CloudFrontのヘッダー・Cookie転送設定
CloudFrontはデフォルトでは一部のヘッダー・Cookieをオリジンに転送しないため、`/api/*`ビヘイビアに以下を明示的に設定する必要がある。
- **Authorizationヘッダーの転送**:JWT Authorizerがトークンを受け取れるようにするため必須。転送を許可しないと全リクエストが認可エラーになる
- **Cookieの転送**:リフレッシュトークン(httpOnly Cookie)を使う`/auth/refresh`・`/auth/logout`等のエンドポイントで必要
- 設定方法:Origin Request Policyで`Authorization`ヘッダーと`Cookie`を転送対象に指定する(AWS管理ポリシーの`AllViewerExceptHostHeader`等が候補)
- **キャッシュ無効化**:`/api/*`ビヘイビアにはAWS管理の`CachingDisabled`ポリシーを適用する。特にランダム受信のようなAPIがキャッシュされると「毎回違う結果が返るはずなのに同じ結果が返る」事故につながるため必須

### 開発順序の方針
変更コストが低い部分(UI・見た目)は後回しにし、変更コストが高い部分(API・DB整合性)を優先する。

1. バックエンド・インフラの実装(DB構築、Lambda、API Gateway、Cognito設定)
2. フロントの骨格をダミーデータで仮組み(画面遷移・コンポーネント配置の確認)
3. API接続(ダミーデータを実際のfetch呼び出しに置き換え)
4. 各コンポーネントのディテール(スタイリング、エラーハンドリング、ローディング表示)

### アニメーションの方針
- 「感想を送る/受け取る」ことを表現する凝ったモチーフ演出(封筒がポストに入る等)は実装しない。優先度が低く、実装コストに対して語れる技術的深さが浅いため
- シンプルなCSSアニメーション(`@keyframes`によるフェードイン、`max-height`による開閉トランジション等)は低コストで実装できるため、骨格が固まった後の仕上げとして検討する
  - 例: `ReviewCard`表示時のフェードインアップ
  - 例: 領域Bの「開封」を`max-height`のtransitionで表現(`isOpen`のtrue/falseで開閉、`isLiked`のトグルと同じ発想)

### useEffectについて
- `useState`/`useContext`が「状態の保持・共有」を担うのに対し、`useEffect`は「特定のタイミングで処理を実行する」ためのもの
- 主な用途:
  - ページを開いた瞬間にログイン状態を確認する(`/auth/refresh`への問い合わせ。副作用がなく安全なため自動実行してよい)
  - 作品検索の入力値(`query`)が変わるたびに、一定時間(300ms)待ってから`/films/search`を呼ぶ(デバウンス)。依存配列に`[query]`を指定することで「特定の値が変わった時だけ実行する」制御ができる(空配列`[]`の「最初の1回だけ」とは異なるパターン)
- **注意:ランダム受信(`POST /reviews/random`)は`useEffect`での自動実行を行わない**。`received_reviews`へのINSERT(消費)という副作用を伴うため、ページ再読み込み・React開発時の再実行・戻る操作・コンポーネント再マウント・読む前の画面離脱等でも意図せず消費されてしまうリスクがある。ユーザーが「感想を受け取る」ボタンを明示的に押した`onClick`の中で呼び出す設計とする

### ランダム受信のフロー(ボタン起点)
```
ページ表示 → フィルタ選択(任意) → 「感想を受け取る」ボタン押下 → POST /reviews/random → ReviewCard表示
```

## films/tagsマスタの運用方針

### films(作品マスタ)
- **A案を採用**:ユーザーは新規作品を自由に追加できない。登録済みの作品からのみ選んで投稿する(タグと同様、表記揺れ防止のため)
- 運営(自分)側が事前に一括投入する。1本ずつの手動INSERTではなく、CSV等でリストを作成し一括インポートする方式を取る
- **規模:興行収入top100(1980〜2026年)ベースで、実データを確認した結果1200本程度しかなかったため、1000本程度に絞ってスタートする**
  - 900本以上観ている自分の鑑賞量を基準にすると母数感覚がズレるため、一般ユーザーの鑑賞率を踏まえて規模を調整した
  - 感想が集まりやすいビッグタイトル中心の構成は、母数の偏り問題(マイナー作品ばかりで感想が集まらない)を回避する上でも都合が良い
  - ビッグタイトル中心でも「見たことのない作品に出会える」余地は残り、当初のセレンディピティという狙いとも合致する
- **初期投入(1000本規模)は打ち止めではない**:リリース後、SNS等で「この作品の感想を書きたい」というリクエストが来た場合、運営(自分)側で`films`への行追加(INSERT 1件)を随時行う。DBスキーマの変更を伴わない単純な追加のため、後から柔軟に対応できる
  - 本サービスは収益化を目的としないため、リクエストに柔軟に応じる運営ができる。「映画好きの人に喜んでもらえること」「映画業界が賑やかになること」を目的に置き、ユーザーとの対話の中でラインナップを育てていく運用を想定する
- **データ収集の方針**:年間興行収入ランキング等の統計データは、AIの知識から直接生成させない(存在しない作品名やランキングの誤りが生じるリスクが高い)。Web検索等で実データを確認したものを、AIには「CSVへの整形」「INSERT文への変換」という変換作業のみ任せる

### tags(タグマスタ)
- 事前定義の選択式(音楽/アクション/演技/脚本/演出/映像美/テンポ/衝撃展開など)。ユーザーの自由入力は不可
